# Flutter Service Architecture Report

This document outlines the architecture generated by the `saed_generator` tool. This architecture is designed to enforce a clear separation of concerns by using a feature-based folder structure, integrating Cubit for state management, and heavily relying on code generation to bootstrap standard CRUD/Get features.

## General Structure

The application adopts a feature-based organization. All generated code for a new service or feature is placed under `lib/features/<feature_name>/` (the `<feature_name>` uses `snake_case` corresponding to the service name). Global configurations are modified in the `lib/core/` and `lib/router/` directories to integrate the new feature.

When a feature (e.g., `user`) is generated, the structure looks like this:

```
lib/
├── core/
│   ├── api_manager/
│   │   └── api_url.dart        # Modified to include API endpoints for the new feature
│   └── injection/
│       └── injection_container.dart # Modified to register the feature's Cubit(s)
├── router/
│   └── app_router.dart         # (or go_router.dart) Modified to include routes for the new feature
└── features/
    └── user/                   # The generated feature folder
        ├── bloc/
        │   ├── user_cubit/     # Handles "Get" state management
        │   │   ├── user_cubit.dart
        │   │   └── user_state.dart
        │   └── users_cubit/    # Handles "CRUD/GetAll" state management
        │       ├── users_cubit.dart
        │       └── users_state.dart
        ├── data/
        │   ├── request/
        │   │   └── create_user_request.dart # Data Models for API requests
        │   └── response/
        │       └── user_response.dart       # Data Models for API responses
        └── ui/
            ├── pages/
            │   ├── user_page.dart    # UI Page for singular view (Get)
            │   └── users_page.dart   # UI Page for plural view (List/GetAll)
            └── widget/
                └── item_user.dart    # Reusable UI widget representing an individual item
```

## Generated Components and Layers

### 1. Data Layer (`lib/features/<feature_name>/data/`)
*   **Request Models (`request/`):** Contains models representing the data sent to the API, typically used in POST/PUT requests (e.g., `CreateUserRequest`).
*   **Response Models (`response/`):** Contains models representing the data received from the API (e.g., `User` and `Users` lists). It utilizes standard `fromJson` and `toJson` serialization.

### 2. Domain / State Management Layer (`lib/features/<feature_name>/bloc/`)
State management is implemented using **Cubit** (specifically a base class `MCubit`).
Depending on the generation type (`Get` vs `CRUD`), different cubits are created:
*   **Item Cubit (`<feature_name>_cubit/`):** Responsible for fetching and managing the state of a single entity. It utilizes a `getData` method to fetch from an API via `APIService`.
*   **Items Cubit (`<feature_name>s_cubit/`):** Responsible for managing lists of entities and full CRUD operations (Create, Read/GetAll, Update, Delete). It manages states like loading, success, and error, and syncs updates to a local cache mechanism.

### 3. Presentation Layer (`lib/features/<feature_name>/ui/`)
*   **Pages (`pages/`):** Standard Flutter UI screens (e.g., `UserPage`, `UsersPage`). They use `BlocProvider`, `BlocBuilder`, and `BlocListener` to reactively build the UI based on the Cubit's state. They incorporate common core widgets like `AppBarWidget` and `RefreshWidget`.
*   **Widgets (`widget/`):** Contains localized UI components used by the pages, such as an item card (`item_user.dart`).

## Core Configuration Integrations

When a new feature is generated, the `FullService` generator automatically updates key core files:

1.  **API URLs (`lib/core/api_manager/api_url.dart`):**
    *   Adds static constants for the new API endpoints (e.g., `Get`, `GetAll`, `Add`, `Update`, `Delete`) grouped under classes like `GetUrl`, `PostUrl`, `PutUrl`, `DeleteUrl`.
2.  **Dependency Injection (`lib/core/injection/injection_container.dart`):**
    *   Registers the newly created Cubits using `GetIt` (`sl.registerFactory(() => ...)`), ensuring they can be injected into the UI or router when needed.
3.  **Routing (`lib/router/app_router.dart` / `go_router.dart`):**
    *   Adds GoRouter route definitions for the new pages. It automatically configures `BlocProvider` wrappers around the pages so the necessary Cubit is injected when the route is accessed.

## Summary

This architecture provides a scalable, standardized approach to Flutter development. By isolating each feature into its own folder with explicit `data`, `bloc`, and `ui` layers, and by automating the wiring of DI, routing, and APIs, it significantly reduces boilerplate and enforces strict separation of concerns.
